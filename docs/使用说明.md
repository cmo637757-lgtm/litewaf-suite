# LiteWAF 使用说明

> 面向：要把这套系统跑起来、演示、或验收的人。
> 环境：Windows 11 宿主 + VMware Workstation 17.5 + Kali Linux 2026.3（用户 `kali`，口令 `kali`）。
> 所有命令都在 Kali 里执行；`/mnt/hgfs/share` 是 Windows 的 `D:\网安综设` 共享盘。

---

## 1. 三分钟启动

前提：虚拟机已开机、共享盘已挂载（`ls /mnt/hgfs/share` 能看到文件）。

```bash
# ① 一次性初始化（只有新装的虚拟机才需要：装依赖、建库、建目录、装 systemd 守护）
sudo bash /mnt/hgfs/share/scripts/kali_setup.sh
sudo bash /mnt/hgfs/share/scripts/s5_init_runtime.sh
sudo bash /mnt/hgfs/share/scripts/console_static.sh          # 首次构建前端静态文件

# ② 一键启动全部服务（幂等：已在跑的自动跳过，约 25 秒）
sudo bash /mnt/hgfs/share/scripts/s10_start_all.sh
```

打开浏览器：**http://192.168.134.140:18082**（生产模式静态站，演示推荐这个）。

`start_all.sh` 会按顺序拉起七个东西，每步都等到端口真正 LISTEN 才继续：MariaDB → WAF 引擎实例（systemd）→ 执行器 → 后端 → 采集器 → 静态站 → Vite（`SKIP_VITE=1` 可跳过最后一项）。最后打一张自检表：

```
  引擎正常请求        200
  引擎拦截 SQLi       403
  平台 health         200
  静态站首页          200
  采集器进程          在
```

停全部（库也一起停；加 `--keep-db` 保留数据库）：

```bash
sudo bash /mnt/hgfs/share/scripts/s10_stop_all.sh
```

**想逐个手动起**（排障时用）：

```bash
sudo systemctl start mariadb              # 库
sudo systemctl start litewaf-runtime      # WAF 引擎（18010，带 systemd 守护）
cd /opt/litewaf/engine && setsid nohup python3 engine_exec.py > /opt/litewaf/engine.log 2>&1 < /dev/null &   # 执行器 18081
cd /opt/litewaf/platform/backend && setsid nohup sudo -u kali java -jar target/platform-0.1.0.jar > /opt/litewaf/platform.log 2>&1 < /dev/null &   # 后端 18080
cd /opt/litewaf/platform/collector && setsid nohup sudo -u kali python3 lwaf_collect.py --config config.ini > /opt/litewaf/collector.log 2>&1 < /dev/null &   # 采集器
```

> 后端与采集器**必须用 `sudo -u kali` 跑**：`/opt/litewaf/runtime/engine.token` 是 `root:kali 640`，root 起反而读得到、但写日志会变成 root 属主，后面 Vite 构建会和它抢文件权限。

| 账号 | 口令 | 角色 | 能做什么 |
|---|---|---|---|
| `admin` | `LiteWaf@2026` | ADMIN | 全部：看板、事件、规则发布、告警、回退 |
| `viewer` | `Viewer@2026` | VIEWER | 只读：看板、事件、告警列表；改任何东西都 403 |

## 2. 五个进程分别是什么

| 进程 | 端口 | 作用 | 挂了会怎样 |
|---|---|---|---|
| Nginx + LiteWAF 引擎 | 18010 | 真正的防护：拦 SQLi/XSS/CC，写两份日志 | 站点打不开；页面数据停止增长 |
| 平台后端（Spring Boot） | 18080 | 统计、事件查询、规则发布、告警、评估与导出 | 页面白屏；引擎防护不受影响 |
| 执行器（Python） | 18081 | 后端唯一的"动手"通道：check/publish/rollback/status | 规则改不了，已在跑的规则照旧生效 |
| 采集器（Python） | — | 每 1 秒 tail 日志，落库 | 页面数据停更，引擎照常拦截 |
| 前端（Vite） | 5173 | 开发模式控制台，改代码即时生效 | 页面打不开，接口仍可用 |
| 控制台静态站（nginx） | 18082 | 生产模式控制台：纯静态文件 + 反代 `/api`，不依赖 Node | 页面打不开；演示推荐用这个 |
| MariaDB | 3306（仅本机） | 请求记录、拦截事件、告警、标记、版本、审计 | 采集器与后端都起不来 |

设计上：**引擎不依赖 Java**。关掉后端和前端，WAF 照常拦截——这一点可以现场演示，也是答辩时的加分项。

演示建议走静态站 `http://192.168.134.140:18082`：它只依赖 nginx，不怕 Node 进程被 OOM 杀掉。

线上实例还装了 systemd 守护（`litewaf-runtime.service`），误杀 nginx 主进程后约 3 秒自动拉回：

```bash
sudo systemctl status litewaf-runtime     # 看守护状态
sudo systemctl restart litewaf-runtime    # 手动重启
```

## 3. 页面怎么用

- **总览**：窗口选「演示数据（F20 固定集）」→ 四个 KPI 应为 `20 / 5 / 25.0% / 0.3333`，耗时卡 `100ms / 190ms / 300μs / 500μs`，分类 SQLi 3 / XSS 1 / CC 1。切「最近 15 分钟」看真实流量。
- **拦截事件**：按时间窗/IP/类型/URI 过滤，点一行进详情（14 个字段 + 同 IP 前后 12 小时关联）。
- **规则与 CC**：左边是规则文件全文，右边是 CC 漏桶三参数。流程固定三步：**检查**（只跑 `nginx -t`，不动线上）→ **发布**（原子替换 + reload + 三次探测，失败自动回滚）→ 可 **回退上一版**。每次动作都在「操作记录」里留一条。
- **告警**：上面是消费器状态（消费到哪条事件、跳过多少历史），中间是规则（阈值/窗口/抑制/Webhook），下面是告警实例。点开能看关联事件、投递记录，可「重新投递」「标记已处理」。
- **误报与调优**：三个指标分开看，别混：`已确认误拦占全部拦截`（确认数 / 全部拦截）、`复核覆盖率`（复核过 / 全部拦截）、`已复核事件的误拦占比`（确认 / 已复核）。覆盖率低的时候，误拦占比不能当整体误报率用——页面右侧有说明。标记入口在事件详情页底部（确认误报 / 驳回 / 撤销标记），标记只加在 `false_positive_marks` 表，**原始拦截事实一个字都不改**。
- **评估报告**：跑 `python3 /mnt/hgfs/share/scripts/s8_eval.py` 生成一次跑分（201 条样本约 3 分钟），页面就能看到混淆矩阵、漏报/误报明细、样本集指纹与历史跑次。每次跑分会留一条历史，横向对比就能看出「补规则前后」的检出变化（当前 rules-v3 39 条：TP=96 FN=4 FP=0，准确率 98.01%）。
  - **跑之前先停手 70 秒**：评估靠连打同一台机器，会让源 IP 进 CC 漏桶，紧接着发布规则时「三次探测」会误判成 403 失败。等一分钟后发布，或先 `sudo systemctl restart litewaf-runtime` 清桶。
- **导出**：拦截事件页右上角「导出 CSV / 导出 JSONL」，导的是当前筛选结果，上限 1 万行（超了会提示缩小范围，不会静默截断）。CSV 带 BOM（Excel 打开中文不乱码）且对 `= + - @` 开头的字段做了公式注入防护。
- **规则试打**（规则与 CC 页下方）：输入一条 URI 打一发，回读「命中哪条规则、什么类别、多少分、为什么拦」。改规则前先确认会不会误伤自己的业务 URL，比发布上线再观察快得多。注意它打的是真实例，会计入 CC 漏桶，短时间内别连打超过容量。
- **性能与数据源**：上半是平台接口耗时（最近 200 次调用的 P50/P95/最慢一次，按 `/api` 统计、`/health` 不计），下半是采集器心跳（轮次、入库行数、解析失败数、每个日志文件的已读/总大小/积压字节）。排查"数据怎么不更新了"先看这一页。
- **崩溃恢复演练**：`sudo bash /mnt/hgfs/share/scripts/s10_crash_drill.sh` 会 kill -9 掉 nginx 主进程，然后等 systemd 拉回、等页面重新出数，实测约 4 秒。演示时可以直接跑，跑完页面数据会自己续上。

## 4. 一条命令验收全链路

```bash
bash /mnt/hgfs/share/scripts/s7_accept.sh              # 全跑（含引擎 14 步，约 5 分钟）
bash /mnt/hgfs/share/scripts/s7_accept.sh --skip-engine # 跳过最慢的引擎验收（约 90 秒）
bash /mnt/hgfs/share/scripts/s7_accept.sh --only alerts  # 只跑某一段
```

会依次检查：进程是否在 → 引擎 200/403 → F20 落库与幂等 → 接口 32 项 + 误报 28 项 + 评估接口 18 项 + 导出 13 项 → 发布闭环 13 项 → 告警 19 项 → 前端可达，最后打一张汇总表（**15 项必选**）。任何必选阶段失败，退出码非 0。

## 5. 手工验证几个关键场景

```bash
# 引擎拦截（注意要带浏览器 UA，否则会被"扫描器"规则先拦掉）
UA='Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 Chrome/120.0 Safari/537.36'
curl -s -o /dev/null -w '%{http_code}\n' -A "$UA" 'http://127.0.0.1:18010/p1'                        # 200
curl -s -o /dev/null -w '%{http_code}\n' -A "$UA" 'http://127.0.0.1:18010/p1?id=1%20UNION%20SELECT...'  # 403

# 按命中次数计分：同一规则命中两次就够了（旧版这条是 200）
curl -s -o /dev/null -w '%{http_code}\n' -A "$UA" 'http://127.0.0.1:18010/p1?id=1%20SELECT%20*%20FROM%20users'  # 403

# 请求体硬上限：超过 8KB 直接 413，日志 reason=body_too_large
python3 -c "print('a'*9000)" > /tmp/big.txt
curl -s -o /dev/null -w '%{http_code}\n' -A "$UA" -X POST --data-binary @/tmp/big.txt 'http://127.0.0.1:18010/p1'  # 413

# 平台接口
curl -s http://127.0.0.1:18080/api/health
curl -s -X POST http://127.0.0.1:18080/api/auth/login \
  -H 'Content-Type: application/json' -d '{"username":"admin","password":"LiteWaf@2026"}'

# 数据库
mariadb --skip-ssl -ulitewaf -p'LiteWaf@2026' litewaf \
  -e "SELECT COUNT(*) AS requests FROM requests; SELECT category_display, COUNT(*) FROM waf_events GROUP BY 1;"
```

> `--skip-ssl` 不能省：MariaDB 11.8 客户端默认走 TLS，本地这套没配证书，不加会报 TLS 握手错误。

## 6. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面能开但数字全是 0 | 采集器没起，或时间窗不对 | 看 `/opt/litewaf/collector.log`；把窗口切到「最近 1 小时」 |
| 某个服务突然不见了 | 单独挂了 | 直接再跑一次 `sudo bash /mnt/hgfs/share/scripts/s10_start_all.sh`，它只补没在跑的那几个 |
| 脚本报 `/tmp/xxx: Permission denied` | 脚本里写了固定 `/tmp` 文件名，被别的用户先占住了 | 已在关键脚本改成 `mktemp`；遇到其他脚本同类报错就手动 `sudo rm -f /tmp/xxx` 再跑 |
| 规则发布一直失败 | 执行器没起（18081）| `curl http://127.0.0.1:18081/status`，看 `/opt/litewaf/engine.log` |
| `ls /mnt/hgfs/share` 报没有那个文件 | 共享盘没挂 | `sudo vmhgfs-fuse .host:/ /mnt/hgfs -o allow_other`，或在 VMware 设置里确认共享文件夹已启用 |
| 所有 curl 都 403 | 用了 curl 默认 UA，命中「扫描器」规则 | 加 `-A` 浏览器 UA |
| 采集器报 TLS 错误 | 连接串没加 `ssl_disabled` | 已在代码里默认关掉；自己写脚本连库时记得关 |
| 后端构建失败 `Could not resolve dependencies` | 没网或镜像慢 | `mvn -s /etc/maven/settings.xml`；或用已构建好的 jar 直接启动 |
| 端口被占用 | 上次没退干净 | `sudo fuser -k 18080/tcp`（别用 `pkill -f jar`，会把 ssh 自己杀掉） |
| 评估报告页是空的 | 还没跑过分，页面只读 `/opt/litewaf/evaluations` | `python3 /mnt/hgfs/share/scripts/s8_eval.py`（约 1 分钟） |
| 误报页三个指标偏差大 | 库里残留旧标记，或窗口选了「全部时间」 | 测试脚本开头会自动清 F20 窗口的标记；日常看 F20 口径就对 |
| 一键验收告警项偶发不通过 | 同一时间桶里残留上一轮测试事件 | `s6_alert_test.py` 已改为先删 `10.99.0.x` 事件再跑，重跑即可 |
| 上传大表单时返回 413 | 引擎新增了请求体硬上限（默认 8KB，`reason=body_too_large`） | 在对应 location 里调大：`lite_waf_max_body_bytes 1048576;` 再 `sudo systemctl restart litewaf-runtime` |
| 同一 IP 突然所有请求都 403 | 被 CC 漏桶封了（默认 20 次/10 秒 → 封 60 秒） | 停手等 60 秒，或 `sudo systemctl restart litewaf-runtime` 清空封禁（重启会清桶） |
| 改完规则文件没生效 | 线上实例读的是 `/opt/litewaf/runtime/rules/`，不是源码目录 | 走「规则与 CC」页的检查 → 发布，或直接 `sudo systemctl restart litewaf-runtime` |
| 首页右上角显示「轮询兜底」而不是「实时」 | SSE 没连上（后端刚重启、或 token 过期） | 等 5 秒会自动重连；仍是兜底就重新登录一次（token 失效时 EventSource 拿不到数据） |
| 日志文件一直涨 | 没装轮转配置 | `sudo bash /mnt/hgfs/share/scripts/s12_logrotate.sh`（装完每天自动轮转、保留 7 份、压缩） |
| 想换 JWT 密钥/数据库口令 | 默认值写在 `application.yml` 的 `${LITEWAF_*:默认}` 里 | `export LITEWAF_JWT_SECRET="$(openssl rand -base64 48)"` 后重跑 `s12_backend_rebuild.sh`；换密钥会让所有旧 token 立即失效 |

## 7. 目录速查

| 路径 | 内容 |
|---|---|
| `/opt/litewaf/src/WAF-lite` | 引擎源码（C 模块 + 规则引擎 + 测试） |
| `/opt/litewaf/runtime` | 线上实例：`conf/` 配置、`rules/` 规则、`versions/` 版本、`candidates/` 候选、`logs/` 日志 |
| `/opt/litewaf/platform/backend` | 平台后端源码 + `target/platform-0.1.0.jar` |
| `/opt/litewaf/platform/frontend` | 前端源码（`dist/` 是构建产物，静态站吃这份） |
| `/opt/litewaf/platform/collector` | 采集器 |
| `/opt/litewaf/engine` | 执行器 `engine_exec.py`（**不是** `platform/executor`，网上教程里那套路径在这里不适用） |
| `/opt/litewaf/evaluations/<run_id>/report.json` | 每次评估跑分的结果，平台只读不算 |
| `/opt/litewaf/state` | 运行时状态（采集器心跳 `collector_status.json`）；`logs/` 是 root:root 755，跑采集器的 kali 用户写不进去，所以状态文件单独放这 |
| `/mnt/hgfs/share` | Windows 侧的 `D:\网安综设`（源码、脚本、文档、截图都在这里） |

常用脚本（都在 `/mnt/hgfs/share/scripts/`）：

| 脚本 | 干什么 | 耗时 |
|---|---|---|
| `s10_start_all.sh` | **一键启动全部服务**（幂等，`SKIP_VITE=1` 跳过 dev server） | 25 秒 |

| `s11_e2e_live.sh` | 真实链路：打 3 条请求 → 等采集 → 查库查接口 | 10 秒 |
| `s8_eval.py` | 带标签样本跑分，出 TP/FN/FP/TN 与 FNR/FPR | 约 1 分钟 |

| `s10_crash_drill.sh` | 崩溃恢复演练：kill -9 → 等守护拉起 → 验证页面出数 | 15 秒 |
| `s10_reset_data.sh` | 采集数据恢复自洽（清表 + 重灌 F20 + 打真实请求） | 30 秒 |

## 8. 备份与恢复

```bash
sudo bash /mnt/hgfs/share/scripts/db_backup.sh          # 备份到 /opt/litewaf/backups/，自动保留最近 7 份
sudo bash /mnt/hgfs/share/scripts/db_backup.sh --list   # 看有哪些备份
sudo bash /mnt/hgfs/share/scripts/db_restore.sh --latest   # 从最近一份恢复
```

恢复会先做一次「安全备份」，再整库导入——误点恢复也能找回来。
答辩前一天建议跑一次备份，把 `litewaf-*.sql` 拷到 Windows 侧存档。

## 9. 卸载 / 重建

```bash
sudo systemctl stop mariadb           # 停库
sudo fuser -k 18010/tcp 18080/tcp 18081/tcp 5173/tcp
sudo rm -rf /opt/litewaf /opt/src     # 删运行目录（源码在共享盘，不受影响）
```

虚拟机层面：关机时用 `sudo poweroff`（别点"关闭电源"，会造成日志损坏），必要时从快照「干净环境」恢复。
